Build notes for the RTS test builds delivered to the user (DSpico), newest first.
Each build's README carried the notes of the builds before it; this is build 33's, the last one,
kept as written for the tester. It records what changed per build, what was measured in melonDS
and on hardware, and the known gaps at each point. Patch numbers refer to the series as delivered
(0001..0048 on top of rasalopa's enhanced-v1.0.0); the same changes are this branch's commits.
After build 33 the branch was rebased (no functional change) and tools/rts-harness was added.

Changed since build 25: _pico/picoLoader9.bin, _pico/picoLoader7.bin and
_pico/rtsmenu9.bin (copy all three), rts_inspect.py, patches 0032-0036.

READ FIRST:
  - States saved with build 25 or older don't load in this one (the menu
    says so). Save new ones.
  - The menu file may now be up to 40 KB, and the loader remakes
    _pico/rtsstash.bin at 232 KB on the first boot. Both happen by themselves.
  - Each game gets a small file next to its states, _pico/states/XXXX.shd
    (a few KB). See "Boot" below. Deleting it is safe: it gets remade.

Saving and loading are faster:
  - A save no longer writes the 2 KB blocks of main memory that are all
    zero. It keeps a map of them, and a load fills those blocks with zero
    instead of reading them. The DSpico writes one sector per card command,
    so writing less is the only way to save faster. In the test games
    27-72% of main memory is skipped (M&L 72%, Chrono Trigger 66%,
    Layton 61%, SM64 50%, Rocket Slime 49%, Pokemon D 46%, Phantom Hourglass
    31%, Advance Wars 30%, Castlevania 27%). Everything else (VRAM, WRAM,
    registers) is about 1 MB and is still written in full. Expect roughly
    half the old save time, less in the games with more zero memory. I
    can't time it on the hardware; please tell me what you see.

Boot:
  - The overlay scan (build 24's boot slowdown) now runs only on the first
    boot of a game. The result is kept in _pico/states/XXXX.shd, and later
    boots read it instead: 1-2.5 s quicker in melonDS (Phantom Hourglass
    2.4 s, Castlevania 2.0 s, SM64 1.9 s, Pokemon 1.5 s, M&L and CT 1.4 s),
    and more on the card, where reading the overlays also takes time. The
    file is used only while the loader, the rom file (size, date, header)
    and the scan all match. A new loader build or a different rom just
    scans again.

Sound after a load:
  - Looping channels (music, ambience) now carry on from where they were
    when you saved, not from the top of the sample. The menu works out how
    far into the loop each channel was and starts it at the next loop point
    that matches, so the music is in step within a few samples. On the DS a
    channel can only start from the top, so a channel that is mid-loop may be
    quiet for up to one loop pass (usually well under a second).
  - A one-shot sound that had already finished stays off instead of playing
    again.

Display registers written by DMA (Phantom Hourglass's fog table, an M&L
engine B clear): the shadow now records what an immediate DMA writes into
those registers, so a load puts them back too.

Timers: the ARM7's timers (behind its OS tick and alarms, which drive
sound) now stop while the menu is open and start again from their saved
counts on the same scanline, so their phase holds after a load. Build 25's
note that the ARM7 tick ran on from the running session's count no longer
applies.

Tested in melonDS with your dumps (load after filling the display registers
with garbage, 2 s compared against an uninterrupted run): screens differing
0-3 of 120 in every game. The ones that differ are frames 0-1 right after
the resume. The save files (GAME.SAV) were byte-identical every time.

USE _pico/picoLoader9.bin THIS TIME, NOT THE CENSUS BUILD. The register
shadow no longer needs the census or any traps, so the frame drops the census
causes (Phantom Hourglass) are gone:
  - At boot the loader scans the game's code, its overlays included, for
    every store to a display register that can't be read back. It replaces
    each one with a branch to a small stub that does the store and keeps a
    copy of the value. Calls into the SDK's copy and fill routines that
    target those registers get a wrapper that does the same. A store costs
    tens of cycles more instead of a ~580-cycle trap, and only when the game
    writes one of those registers.
  - On a load the saved values go back, as with the census build.
  - census-test/ is kept only to measure with; it doesn't have the new
    shadow or the sound fix.

Sound after a load: the ARM7's sound registers (each channel's sample
address, pitch, loop start and length, the timer reloads, sound capture)
can't be read back either. Until now a load stopped every channel and only
new notes came back, so music and held sounds stayed silent (SM64 had no
sound at all). The loader now shadows those on the ARM7 the same way. When
the menu closes after a load, it starts the channels the state had playing
again. They restart from the top of their sample, because the DS doesn't
keep a playback position you can restore, so a held note or a streamed track
can be out of step for a moment until the game moves on.

Tested in melonDS with your dumps, loading after filling the display
registers with garbage (as if loading from another scene). Screens that
differ in the 2 s after the load: Rocket Slime (4 points) 1-2, SM64 1,
Pokemon D 0, Layton 1, Chrono Trigger 0, M&L 1 (49 with build 23's
shadow-less loader: its engine B affine and window registers), Castlevania
1, Phantom Hourglass 2, Advance Wars 1. The one frame is the
first frame after the resume.
Sound level after a load against the reference: every game now within a few
percent (it was 56-88% for Pokemon, Advance Wars, Phantom Hourglass and Rocket
Slime, and 0 for SM64).

Things to know:
  - Booting takes longer: the loader reads and scans every overlay (see
    build 25's note at the top for how long).
  - Save new states with this build: states from build 23 or older don't
    have the new shadows, so their display and sound registers stay as the
    running session had them, which is the old behaviour.
  - Not covered yet: a display register that only a DMA writes (Phantom
    Hourglass's fog table, an engine B clear in M&L). Those keep the running
    session's values after a load.
  - The timer that drives the ARM7's OS tick runs on from the running
    session's count. Nothing visible came of that in testing.

Changed since build 21: census-test/picoLoader9.bin and rtsmenu9.bin
(_pico/picoLoader9.bin only gains a log line; picoLoader7.bin is the same).
Build 20's white screen is found and fixed, using melonDS run as a DSi with
your BIOS dumps and the DSpico's card commands:
  - On a DSi the loader keeps the DSi's own BIOS for the exit combo. Its
    exception handler pushes onto a stack at 0x02FFFD9C before it turns the
    protection unit off; the DS BIOS uses 0x027FFD9C, which DS games map.
    No DS game maps 0x02FFFD9C, so the census's very first trapped write
    faulted again inside the BIOS, forever: a white screen in every game,
    on a DSi only. The census now maps that page for the BIOS (it reuses
    protection region 2, the SDK's guard over the ARM7's corner).
  - The DSpico's card read code resets protection region 3 on every ROM
    read, the same region the census borrows for the IO registers, so the
    census stopped at the first card read (on a DS too). Census builds no
    longer do that while the census holds the region.
  - The menu now says "Census: stopped (A: why)" when the census stopped,
    instead of "traps on".
In the emulated DSi, SM64DS and Advance Wars boot with the census on and it
keeps counting. To try it, copy census-test/picoLoader9.bin over
_pico/picoLoader9.bin. The census also traps the DSpico's own card writes, so
loading screens are slower with it on; its numbers include that.
On a DSi the counts also include the DSi BIOS's wait-for-interrupt routine,
which writes two registers each time a game idles, so DSi numbers run higher
than a DS's for the same game (Advance Wars: ~1700 a frame at most vs ~800).

THE CENSUS (DS games built with the normal Nintendo SDK; not DSi-enhanced ones)
From boot, every ARM9 write to the first 8 KB of IO (2D, DMA, timers, 3D,
etc.) traps, is done by a small handler and counted. It's a measurement: the
game runs a little slower while it's on, and that slowdown is what we want to
know.
 1. Boot a game and play normally. Try a calm scene (walking around, a menu)
    and a busy one (a battle, lots of 3D, a cutscene).
 2. Open the menu (L+R+Up+Select), go down to "Census: traps on" and press A.
    It writes a report to /_pico/rtslog.txt (section 5, "RTS register-write
    census") covering the time since boot or the last report, and the counts
    start again. The two lines under the menu give the short version: traps
    per frame and the estimated cost.
 3. Start on that item turns the traps off/on, so you can feel or film the
    difference in the same scene. While the menu is open the traps pause.
 4. A report per scene is ideal: open the menu and press A right after the
    calm part, play the busy part, press A again (each report replaces the
    last one in rtslog.txt, so send me the file in between, or note the
    numbers from the screen).
Good games for this: Advance Wars: Dual Strike (2D), Rocket Slime (2D with
fades), Phantom Hourglass (3D, the worst case).

The census stops by itself, and the report says why, if the game uses the
GBA slot, changes the protection unit itself, or runs a store the handler
doesn't know. Games keep running normally when it stops. If a game misbehaves
only with this build, turn the traps off with Start and tell me which game.

What the report holds: how many cycles one trap costs (measured at boot),
traps per frame on average and in the busiest frame, the share of each frame
that costs, how frames spread by trap count, and which code addresses and
registers write most often.

The restore test (from build 15) checks on the real DS that a load puts back
what it should, and that the game then runs exactly as it did the first time.

Install: copy the _pico folder's six files into /_pico on the DSpico's SD card.
The DS ARM7 BIOS at /_pico/biosnds7.rom is still needed for encrypted roms.
Each game now gets three 5 MB files in /_pico/states (<code>-1.rts is your
save slot, -2 and -3 belong to the test), made on that game's first boot with
this build, plus one shared /_pico/rtslog.txt.

In a DS game:
  L+R+Up+Select    (hold ~3/4 s)  the game pauses, the menu shows on top
      let go of every key first, then
      Up/Down       choose
      A             Resume / Save state / Load state / Test: save + reference /
                    Test: load + compare / Census (report) / Exit to launcher
      Start         on the Census item: traps on/off
      B             back to the game
  L+R+Right+Select (hold ~3/4 s)  exit to the launcher directly, as before

HOW TO RUN THE TEST (one game at a time)
 1. Get to a calm spot in the game: nothing you need to press for a few
    seconds (standing in a room, a menu, a cutscene that plays by itself).
 2. Open the menu, choose "Test: save + reference". It saves slot 1 and the
    game goes on. DON'T TOUCH ANYTHING: about 2 seconds later the game pauses
    by itself, the menu writes slot 2 ("Reference saved to slot 2.").
    Press B.
 3. Play on a bit, or go somewhere else. Then open the menu and choose
    "Test: load + compare", and A again to confirm. It loads slot 1, checks
    memory ("Checking memory..."), and the game goes on from the save.
    DON'T TOUCH ANYTHING again: 2 seconds later it pauses by itself, writes
    slot 3 and compares (about 10 seconds). Two lines show the result:
      "Load check: ..."  did everything the load put back land and stay
                         (memory before resuming, registers just after)
      "Run: ..."         did the game do exactly the same in those 2 seconds
                         as after the original save
 4. Send me /_pico/rtslog.txt (a text file; it holds the latest load check
    and comparison, plus the ones before them, with addresses and values).

Opening the menu yourself during either 2 second wait stops the test.
Notes:
  - "Run: ... differ" isn't automatically a bug: games that take randomness
    from the clock or count real time will differ a little. Running step 3
    twice tells those apart: a real restore gap differs the same way each time.
  - The registers the DS can't read back (scroll, windows, fades, 3D settings)
